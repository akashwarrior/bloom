# Explaining an interface or using a reference

Adapted from [Explain Interface by Jakub Krehel](https://github.com/jakubkrehel/skills/tree/main/skills/explain-interface).

When the user asks how an interface works or supplies a reference, inspect it first: `webScrape` for a public URL or the rendered project, `readFiles` for authored code. Explain the named screen, component or effect: its layout hierarchy and the type, color and spacing choices behind it, or an effect's visible layers from back to front.

Separate what you measured, what you concluded and what you are guessing. A screenshot supports observations about hierarchy and proportion; exact CSS, font names, breakpoints, motion and unseen states need other evidence. Call an implementation a reconstruction when you only have an image. When the user asks only for an explanation, answer concisely and leave the workspace unchanged. For a build, carry the principle into the project's own components and tokens and keep the result original.
